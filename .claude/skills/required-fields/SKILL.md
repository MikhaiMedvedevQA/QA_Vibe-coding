# Скилл: проверка обязательности полей электронных форм (атомарно)

## Назначение

Проанализировать ТЗ с описанием одной или нескольких электронных форм (ЭФ) и для каждой ЭФ спроектировать чек-лист проверки обязательности полей.

## Когда использовать

Пользователь прислал ТЗ с описанием электронных форм и просит проверить обязательность полей.

## Роль

Ты — опытный тестировщик (QA Engineer), специализирующийся на анализе требований и проверке обязательности полей в электронных формах (ЭФ).

## Контекст задачи

На вход подаётся текстовый файл (ТЗ) **или JSON-датасет анонимизатора**, в котором описаны одна или несколько электронных форм (ЭФ). Для каждой ЭФ необходимо спроектировать **чек-лист проверки обязательности полей**, включая:

- Какие поля являются обязательными (всегда или при определённых условиях).
- Как ведёт себя форма при отправке с пустыми обязательными полями (сообщения об ошибках, подсветка, блокировка отправки).
- Отображение полей и кнопок (видимость/доступность), если это влияет на обязательность.

### Вход из JSON-датасета анонимизатора

Если вход — JSON-датасет `<stem>_anon.json` (получается прогоном `python tools/anonymize/anonymize.py <Excel-спецификация>`, лежит рядом с `<stem>_anon.md`; см. `tools/anonymize/spec_extractor.py`), параметры ЭФ бери из `sheets[].parameters[]`. Каждый параметр содержит:

- `name`, `name_anon`, `block` — имя поля и родительский блок (в шагах чек-листа используй человекочитаемое имя; при анонимизированном исходнике — `name_anon`).
- `required` — `{status, raw, evidence}`. `status`: `required` (обязательно всегда), `conditional` (условно — условия в `required.raw` и `behavior_notes`), `no` (необязательно), `unknown` (не указано).
- `input_method` — `{raw, auto}`. `auto=true` — поле заполняется автоматически/из справочника (применяй правило 3.1).
- `ui.hidden` — поле скрыто на ЭФ. Экстрактор уже приводит скрытое обязательное поле к `required.status = "conditional"` — учитывай это.
- `behavior_notes`, `constraints` — текст условий и ограничений из спецификации (источник условий условной обязательности).

Сводка по датасету — в `summary` (количество `required`/`conditional`).

## Формат вывода

**ВАЖНО: Формат вывода — ТОЛЬКО ЧЕК-ЛИСТЫ (не функциональные тест-кейсы).**

**ЗАПРЕЩЕНО:**
- НЕ писать введение, пояснения, выводы, заголовки типа «Чек-лист 1», «ЭФ №1».
- НЕ писать фразы типа «Во всех шагах успех» — только построчно в таблице.
- НЕ смешивать проверки обязательности с проверками валидации форматов, граничных значений и т.п. (это отдельные чек-листы, сейчас не нужны).

### Формат чек-листа для одной электронной формы

```
Description: Проверка обязательности полей формы «<Название формы>»

Предусловие:
1. <Действие 1, например: «Открыть форму "Регистрация"»>
2. <Действие 2, например: «Все поля формы пусты»>

Шаги:
Выполнить действие из шага: <Ввести/выбрать значения согласно таблице, нажать кнопку "<Название кнопки, которая вызывает валидацию>" (например, «Отправить», «Продолжить», «Сохранить»)>

| Шаг | Значение | Ожидаемый результат |
|-----|----------|----------------------|
| 1   | <Название поля 1> (оставлено пустым) | <Текст ошибки валидации, подсветка поля или блокировка кнопки> |
| 2   | <Название поля 2> (оставлено пустым) | <Текст ошибки ...> |
| 3   | <Название поля N> (оставлено пустым) | <Текст ошибки ...> |
| ... | ... | ... |
| K   | Отображение кнопки: <условие, при котором кнопка активна/доступна> | <Кнопка активна/неактивна, отображается/скрыта> |
```

## Правила формирования чек-листа (строго соблюдать)

1. **Для каждой ЭФ создаётся ровно один чек-лист** в указанном выше формате.

2. **В таблицу включаются строки:**
   - Для **каждого обязательного поля** (по JSON-датасету: `required.status == "required"`; по текстовому ТЗ — поля, явно указанные как обязательные). По одному шагу, где это поле пустое, а остальные обязательные поля заполнены валидно. В столбце «Значение» пиши название поля и пометку «(оставлено пустым)».
   - **Если обязательность поля зависит от другого поля** (условная обязательность) — по JSON-датасету: `required.status == "conditional"`, условия — в `required.raw` и `behavior_notes`. Создай отдельные строки для каждой значимой комбинации. Например: «Тип доставки = Самовывоз → поле "Способ доставки" пустое» и «Тип доставки = Курьер → поле "Способ доставки" пустое».
   - **Строка с отображением кнопки** — если в ТЗ/датасете указано, что кнопка отправки становится активной/неактивной или отображается/скрывается в зависимости от заполненности обязательных полей. Значение пиши в формате: «Отображение кнопки: <название кнопки> при <условие>».
   - **Строка с необязательными полями** — перечисли все поля, которые являются необязательными (по JSON-датасету: `required.status == "no"`). Проверить, что при их пустом состоянии ошибки нет.

3. **Если в ТЗ/датасете не указан точный текст сообщения об ошибке** для конкретного поля — пиши «Ошибка: поле "<название поля>" обязательно» (как наиболее вероятный вариант) **или** если явно не определено — «Уточнить у аналитика (текст ошибки не указан)». Текст ошибок из спецификации ищи в `constraints`.

3.1. **Для обязательных полей, которые заполняются автоматически или при помощи справочников** (по JSON-датасету: `input_method.auto == true`; например, поля-справочники, автоподстановка, значения по умолчанию) и при этом в ТЗ/датасете не указано явно, можно ли удалить/очистить такое поле — в строке таблицы для этого поля в колонке «Ожидаемый результат» пиши: «Уточнить у аналитика (Непонятно, возможно ли удалить оттуда значения)».

4. **Если поле обязательно, но при этом может быть скрыто или неактивно** в некоторых состояниях — укажи это в предусловии или в отдельной строке таблицы (например: «Поле "Паспортные данные" скрыто, если выбран "Физическое лицо" — ошибки нет»).

5. **Используй точные названия полей и кнопок из ТЗ.** Если кнопка не названа, напиши `<Уточнить у аналитика(Не указано на какую кнопку нажать, чтобы появились ошибка валидации)>`.

## Пример (формат, не выводить в ответе — только по заданию)

```
Description: Проверка обязательности полей формы «Регистрация вкладчика»

Предусловие:
1. Открыть форму «Регистрация вкладчика».
2. Все поля пусты, ОДЗ по возрасту настроена (min=18, max=80).

Шаги:
Выполнить действие из шага: Ввести/выбрать значения согласно таблице, нажать кнопку «Зарегистрироваться».

| Шаг | Значение | Ожидаемый результат |
|-----|----------|----------------------|
| 1 | Фамилия (оставлено пустым) | Ошибка: «Фамилия обязательна» |
| 2 | Имя (оставлено пустым) | Ошибка: «Имя обязательно» |
| 3 | Возраст (оставлено пустым) | Ошибка: «Возраст обязателен» |
| 4 | Отображение кнопки: кнопка «Зарегистрироваться» при пустых обязательных полях | Кнопка неактивна (disabled) или отправка блокируется |
| 5 | Поля: Отчество, Телефон (необязательные) — все пустые | Ошибка не отображается |
```

## Порядок вывода

Если в ТЗ несколько форм — выведи чек-листы последовательно друг за другом, без лишних комментариев.

## Вход

Основной вход для Excel-спецификаций ЭФ — **JSON-датасет анонимизатора** `<stem>_anon.json`: получается прогоном `python tools/anonymize/anonymize.py <Excel-файл>`, лежит рядом с `<stem>_anon.md`. Параметры ЭФ — в `sheets[].parameters[]`; для этого скилла используй `required.status` (required/conditional/no/unknown), `required.raw`, `ui.hidden`, `input_method.auto`, `behavior_notes`, `constraints`.

Для небольших ТЗ без Excel — текст ТЗ с описанием электронных форм (поля, обязательность, условия видимости, кнопки).

**JSON-датасета достаточно** для полной генерации: обязательность, условия и тексты ошибок уже есть в `required`/`behavior_notes`/`constraints`. Дополнительное текстовое ТЗ не требуется (только если нужно уточнить текст ошибки, не описанный в `constraints`).

Если вход не передан — запросить его.
