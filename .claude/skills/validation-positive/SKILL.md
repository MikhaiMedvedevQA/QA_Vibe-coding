# Скилл: позитивные чек-листы валидации (атомарные, только happy path)

## Назначение

Спроектировать детальные **только позитивные** тест-кейсы и чек-листы для валидатора данных (форма, API-эндпоинт, XML/JSON-схема, банковский перевод, расчёт скидки, валидация конфигурационного файла).

## Когда использовать

Пользователь прислал описание валидатора (поля, правила, ограничения) и просит подготовить позитивные проверки / чек-листы валидации.

## Роль

Ты — опытный тестировщик (QA Engineer), специализирующийся на проверке валидации данных, бизнес-правил и поведения интерфейса/API.

## Контекст задачи

Необходимо спроектировать детальные **только позитивные** тест-кейсы (или чек-листы) для валидатора [описание сущности: форма регистрации, API-эндпоинт, XML/JSON-схема, банковский перевод, расчёт скидки, валидация конфигурационного файла].

Входные данные и ограничения — поля/правила, например:
- Поле «Возраст»: от 18 до 65 лет, целое число, обязательное.
- Поле «Email»: формат user@example.com, максимум 50 символов.
- Код страны: RU, BY, KZ (только эти три).

### Вход из JSON-датасета анонимизатора (для ЭФ)

Если валидатор — электронная форма, описанная Excel-спецификацией, входом служит JSON-датасет `<stem>_anon.json` (прогон `python tools/anonymize/anonymize.py <Excel-файл>`, рядом с `<stem>_anon.md`; см. `tools/anonymize/spec_extractor.py`). Параметры ЭФ — в `sheets[].parameters[]`; для валидации используй:

- `name`, `type` — имя и тип поля;
- `constraints` — тексты ошибок и ограничения (источник ожидаемых результатов и текстов ошибок);
- `behavior_notes` — правила, ОДЗ, условия, особенности поведения;
- `required`, `availability`, `input_method.auto` — обязательность/доступность.

JSON даёт имена/типы/ограничения/ошибки, но точные граничные значения, форматы, ОДЗ, маски могут быть описаны не полностью — для исчерпывающего покрытия валидации желательно дополнительное текстовое ТЗ. Если спецификация полная (поведение + ограничения + ошибки в ячейках) — JSON один покроет.

## Цель

Покрыть все критичные проверки, включая:

- Валидацию значений (формат, диапазон, допустимые символы).
- Обязательность полей (при каких условиях поле обязательно; если зависит от других полей — проверить все комбинации).
- Доступность и видимость полей (активно/неактивно, отображается/скрыто, доступно только для чтения).
- Особое поведение (автозаполнение, маски ввода, динамическая настройка ограничений через ОДЗ, условная валидация).
- Бизнес-правила (например, если поле А заполнено, то поле Б становится обязательным; и т.д.).
- Обработку ошибок (сообщения, подсветка полей, блокировка отправки формы, HTTP-коды ответа).

## Формат вывода

**ВАЖНО: Формат вывода — преимущественно ЧЕК-ЛИСТЫ, а не развёрнутые функциональные тест-кейсы.**

**ЗАПРЕЩЕНО:**
- НЕ писать введение, пояснения, выводы, заголовки типа «Чек-лист 1», «Тест-кейс 1».
- НЕ писать фразы типа «Во всех шагах успех» — только построчно в таблице.

### Формат чек-листа

```
Description (что проверяем):
<Текст требования одной строкой>
Предусловие:

<Действие 1> <Действие 2>
Шаги:
Выполнить действие из шага: <Ввести в поле "Название поля" значение из шага и нажать "Сохранить" / Отправить запрос с параметром из шага>
| Шаг | Значение | Ожидаемый результат |
|-----|----------|----------------------|
| 1   | <значение 1> | <результат 1> |
| 2   | <значение 2> | <результат 2> |
| ... | ... | ... |
```

## Правила формирования чек-листов

- Писать **только позитивные** тест-кейсы. Негативные кейсы не писать.
- **ВАЖНО: должно быть как минимум 1 чек-лист (Позитивные проверки).** Негативными считаются те проверки, которые приводят к какой-либо ошибке. **Если нет однозначного ответа, приводит ли проверка к ошибке — автоматически причисляем её к позитивной проверке.**
- **Применяй декомпозицию по категориям** (валидация / обязательность / доступность / особое поведение и т.д.) и для каждой категории создавай отдельный чек-лист.
- **Если система имеет несколько полей с взаимосвязями** — создавай отдельные чек-листы для комбинаций (обязательность, условная видимость, взаимозависимости) и размещай их в категории «Особое поведение».
- **Для проверки доступности/видимости поля** используй значения: «Поле отображается», «Поле скрыто», «Поле неактивно (disabled)», «Поле только для чтения (readonly)».
- **Для проверки обязательности** добавь шаги, где поле оставлено пустым, и проверь, появляется ли ошибка. Если обязательность зависит от другого поля — создай таблицу решений (ИЛИ pairwise) для комбинаций.
- **Для особого поведения** (динамические ограничения, маски, автопреобразование) — опиши конкретные шаги, например: «Ввести значение 18, изменить ОДЗ на min=21, проверить, что предыдущее значение стало невалидным».
- В **Значение** перечисляются короткие проверки: граничные значения, пустые поля, пробелы, спецсимволы, инъекции, null, латиница/кириллица, эмодзи, буква «ё», копирование/вставка, регистр, длинные строки, отрицательные числа и т.д. (см. пример).
- Если в требованиях нет однозначного ответа, как система должна обрабатывать конкретный случай (например, сообщение об ошибке не указано) — пишем **«Уточнить у аналитика»**.
- Наименование в шагах должно быть в виде «Пустое поле (Значение: "")», «Только пробелы (Значение "   ")», а не просто "" и "   ".
- **Обязательно включай позитивные проверки (валидные данные).**

## Пример шаблона чек-листа (для одного поля)

```
Description:
Поле "Название продукта" — обязательное строковое поле, макс. длина 50 символов, допустимы буквы, цифры, пробелы.
Предусловие:

Авторизоваться в системе. Открыть форму создания продукта. Ввести в поле "Название продукта" значение из шага. Перейти к отображению ошибки.
Шаги:
Выполнить действие из шага:
| Шаг | Значение | Ожидаемый результат |
|-----|----------|----------------------|
| 1 | Пустое поле (Значение "") | Ошибка: поле обязательно |
| 2 | Максимальное значение (Значение "50 символов") | Успех |
| 3 | Больше максимального значения на 1 (Значение: 51 символ) | Уточнить у аналитика |
| 4 | Меньше минимального значения на 1 (Значение: если есть мин. длина) | Уточнить у аналитика |
| 5 | Только пробелы (Значение: "   ") | Уточнить у аналитика |
| 6 | Пробел в начале (Значение: " тест") | Уточнить у аналитика, так как нет однозначного поведения |
| 7 | Пробел в середине (Значение: "тест тест") | Уточнить у аналитика |
| 8 | Пробел в конце (Значение: "тест ") | Уточнить у аналитика |
| 9 | XSS-инъекция (Значение: `<script>alert("test")</script>`) | Уточнить у аналитика |
| 10 | SQL-инъекция (Значение: `select * from dbo.test`) | Уточнить у аналитика |
| 11 | Только латиница (Значение: `product`) | Успех (если латиница разрешена) / Уточнить у аналитика |
| 12 | Только кириллица (Значение: `продукт`) | Уточнить у аналитика |
| 13 | Спецсимволы (Значение: `@ \ / ! # $ ^ & * : ; "`) | Уточнить у аналитика |
| 14 | Непонятные символы (эмодзи/юникод) (Значение: `◕‿◕`, `😀`) | Уточнить у аналитика |
| 15 | Отрицательные значения (Значение: '-123') | Уточнить у аналитика |
| 16 | Буква "ё" (Значение: `ёлка`, `подъезд`) | Уточнить у аналитика |
| 17 | Копировать/вставить значение | ПОВЕДЕНИЕ АНАЛОГИЧНО РУЧНОМУ ВВОДУ (ВСЕГДА ПИСАТЬ ТАКОЙ ТЕКСТ) |
| 18 | БОЛЬШИЕ и маленькие буквы (Значение: `ПрОдУкТ`) | Уточнить у аналитика |
| 19 | Много текста (Значение: 255 символов) | Уточнить у аналитика |
| 20 | Минимальное значение (Значение: "17") | Уточнить у аналитика |
| 21 | Значение внутри диапазона (Значение: "35") | Успех |
| 22 | Дробное число, разделитель точка (Значение: "25.5") | Уточнить у аналитика |
| 23 | Дробное число, разделитель запятая (Значение: "25,5") | Уточнить у аналитика |
| 24 | Ноль (Значение: "0") | Уточнить у аналитика |
| 25 | Значение с ведущими нулями (Значение: "025") | Уточнить у аналитика |
| 26 | Число прописью с заглавной буквы (Значение: "Двадцать") | Уточнить у аналитика |
| 27 | NaN (Значение: "NaN") | Уточнить у аналитика |
| 28 | Null (Значение: null) | Уточнить у аналитика |
```

## Дополнительные примеры чек-листов

### Чек-лист для проверки обязательности поля в зависимости от другого поля

```
Description:
Поле «Способ доставки» обязательно, если выбран «Самовывоз», и необязательно, если выбран «Курьер».
Предусловие:

Авторизоваться в системе. Открыть форму оформления заказа. Выбрать значение поля «Тип доставки» согласно шагу.
Шаги:
Выполнить действие из шага: Заполнить поле «Способ доставки» (если оно отображается) и нажать «Оформить».
| Шаг | Значение (Тип доставки → Способ доставки) | Ожидаемый результат |
|-----|-------------------------------------------|----------------------|
| 1 | Самовывоз → оставить пустым | Ошибка: «Укажите способ доставки» |
| 2 | Самовывоз → указать «Пункт А» | Успех |
| 3 | Курьер → оставить пустым | Успех (поле необязательно) |
```

### Чек-лист для проверки доступности поля

```
Description:
Поле «Промокод» недоступно (disabled), пока не заполнено поле «Email».
Предусловие:

Открыть форму регистрации. Поле «Email» пустое.
Шаги:
Выполнить действие из шага: Проверить состояние поля «Промокод».
| Шаг | Значение | Ожидаемый результат |
|-----|----------|----------------------|
| 1 | Поле «Промокод» без заполненного Email | Поле неактивно (disabled), нельзя ввести текст |
| 2 | Заполнить Email валидным значением | Поле «Промокод» становится активным |
```

### Чек-лист для особого поведения (динамическая настройка через ОДЗ)

```
Description:
Максимальный возраст вкладчика настраивается через ОДЗ. При изменении ОДЗ существующие значения должны перепроверяться.
Предусловие:

Открыта форма редактирования профиля вкладчика. В поле «Возраст» ранее было введено значение 75. ОДЗ настроена: min=18, max=80 (валидно).
Шаги:
Выполнить действие из шага: Изменить ОДЗ (max) и сохранить форму.
| Шаг | Значение (новый max) | Ожидаемый результат |
|-----|----------------------|----------------------|
| 1 | max=80 | Успех (75 ≤ 80) |
| 2 | max=75 | Успех (75 ≤ 75) |
```

### Пример функционального тест-кейса (когда чек-листа недостаточно)

```
Функциональный тест-кейс №1:
Description: Проверка полного сценария заказа с условной обязательностью поля «Адрес доставки».
Предусловие: Пользователь авторизован, корзина не пуста.
Шаги:

1. Перейти в оформление заказа. Ожидаемый результат: открыта форма оформления.
2. Выбрать тип доставки «Самовывоз». Ожидаемый результат: поле «Адрес доставки» скрыто или неактивно.
3. Выбрать тип доставки «Курьер». Ожидаемый результат: поле «Адрес доставки» стало обязательным и активным.
4. Оставить поле «Адрес доставки» пустым, нажать «Оформить». Ожидаемый результат: ошибка «Укажите адрес доставки».
5. Заполнить адрес, нажать «Оформить». Ожидаемый результат: заказ успешно создан.
```

## Вход

Основной вход:
- для ЭФ из Excel-спецификации — **JSON-датасет анонимизатора** `<stem>_anon.json` (имена/типы/ограничения/ошибки в `behavior_notes`+`constraints`) **+ опциональное текстовое ТЗ** с явными правилами валидации (длина, формат, ОДЗ, маски) для полноты покрытия и снижения «Уточнить у аналитика»;
- для валидаторов API/схем/конфигов — текстовое описание полей, правил, ограничений, бизнес-логики.

Если вход не передан — запросить его.
